## Phases

### Phase 1 — Foundation · done

- Next.js 16 App Router, React 19, strict TypeScript, Tailwind v4.
- Design token layer in `app/globals.css`, light and dark, all pairs meeting WCAG AA.
- App shell with a desktop sidebar, a mobile top bar and a mobile bottom bar.
- Domain types for all thirteen entities, Zod schemas, `ApplyPilotRepository` interface.
- Demo storage adapter with a seeded, fully fictional workspace.
- `/`, `/login`, `/onboarding`, `/dashboard`.

### Phase 2 — Planning workspace · done

- `/colleges` with search, status and tag filters; create, edit, delete.
- `/colleges/[collegeId]` with applications, linked essays, notes, last-verified date.
- `/applications` in table and status-board views, filterable by status and round.
- `/applications/[applicationId]` with the requirement checklist and recommender links.
- Dashboard calculations, all of them plain counts.

Checklist completion is `completed required items / total required items`. Items marked
"not needed" leave both sides of the fraction, and the row says so. Verified in a browser:
0/3 → 0/4 after adding a requirement → 1/4 (25%) after completing one.

### Phase 3 — Writing workspace · done

- `/essays` with filters by status and college, live counts, last-edited dates.
- `/essays/[essayId]` with brainstorm, outline, draft, coach and versions tabs.
- Debounced autosave that dedupes and queues rather than dropping writes.
- Version history where **restore is additive**: the current draft is saved as its own version
  first, so restoring cannot lose writing.
- `/activities` with reordering, per-activity configurable character limits, live counters.

### Phase 4 — Planning tools · done

- `/recommendations`, tracking the request only. The letter itself is never stored.
- `/scholarships` with amounts, deadlines in their own time zone, source links, last-verified
  dates, and a standing note that listings close without warning.
- `/calendar` with month and agenda views, per-type filters, and click-to-add on a day.
- Tasks with optimistic completion; a just-ticked task stays visible so the tick is confirmed.

Every deadline shows its year and the time zone it was recorded in. Application and scholarship
deadlines keep the zone the college stated them in; the student's own dates use their profile zone.

### Phase 5 — AI coaching · done

- Server-only `AIProvider` seam with an Anthropic implementation and a deterministic offline coach.
- Six modes: Profile, College Research Organizer, Essay Brainstorm, Essay Feedback, Activities
  Description, Deadline Planning.
- Zod-validated structured outputs. No score, rating or admission-likelihood field exists in any
  output contract — a unit test asserts this by scanning every schema's keys.
- "Show what will be sent" preview, generated by the same server function that builds the real
  request.
- Opt-in draft attachment, per-user rate limiting, timeouts, and a retry state when a model returns
  something unparseable.

The offline coach is what runs with no API key. It derives every line from the student's own text by
rule — quoting, counting, cutting, flagging vague phrasing — and therefore cannot invent an
achievement. Tests assert it introduces no digits the student did not write.

### Phase 6 — Production persistence · done, but see limitations

- `supabase/migrations/0001_init.sql`: thirteen tables, enums, indexes, `updated_at` triggers.
- `supabase/migrations/0002_policies.sql`: RLS enabled and forced on every table, owner-only
  policies, ownership check constraints, a signup trigger for the profile row.
- `SupabaseRepository` implementing the same interface as the demo adapter.
- Magic-link sign-in, `/auth/callback`, session-refresh middleware.
- `npm run db:setup` prints the migration steps.

The app boots and is fully usable with no Supabase configuration at all.

### Phase 7 — QA and polish · done

Domain and security passes were run over the finished application. Findings and fixes are in
`docs/QA_REPORT.md`. The substantive fixes were four colour-contrast failures — including white
text on the dark-mode primary button at 2.09:1 — and four ambiguous "Download" buttons.

### Phase 8 — Desktop build · done

Added after the MVP, in response to a request for an executable. A third storage adapter (`file`)
behind the existing `ApplyPilotRepository` seam, and an Electron shell that runs the same standalone
Next server on loopback. Nothing under `app/` or `components/` changed to accommodate either, which
is the strongest evidence the seam was worth building.

Driving the packaged app turned up a bug that predated the desktop work: six list components
rendered the same `<Dialog>` element twice — once in the toolbar, once as the empty state's action —
so two modals opened together and, between them, marked the entire document `aria-hidden`. The demo
workspace is seeded, so the empty branch had never run in the e2e suite; a desktop user starts there
every time. Fixed in all six, with a regression test in `e2e/core-flows.spec.ts`.

## Known limitations

1. **The Supabase adapter has never run against a live Supabase project.** No credentials were
   available in the build environment. The adapter is written and type-checked, the migrations and
   RLS policies are committed, and the demo adapter's user-scoping behaviour is tested — but the
   Postgres path itself is unexercised. Before trusting it, apply both migrations and verify
   isolation directly: sign in as two users and confirm that pasting one user's record id into the
   other's URL returns the not-found page.

2. **The Anthropic provider has never made a real API call.** No `ANTHROPIC_API_KEY` was available.
   Prompt construction, output-schema validation and error mapping are unit-tested; the network path
   is not. Every coaching flow shown working was the offline coach.

3. **Demo data is in-memory.** It does not survive a server restart, expires after 12 hours, and is
   capped at 500 concurrent workspaces. That is correct for a disposable demo and wrong for anything
   else, which is why real use needs either Supabase or the desktop build's file storage.

4. **The Windows package has never been run on Windows.** No Windows machine and no Wine were
   available. `electron-builder --win` does produce a real `ApplyPilot.exe` (PE32+ x86-64, correct
   version resource and icon) from the same `desktop/main.js`, the same standalone server and the
   same `electron-builder.yml` as the Linux package — and the Linux package is driven end to end by
   `npm run test:e2e:desktop`: the window opens, the server boots, first run reaches onboarding, a
   college is added, the app is **quit and reopened and the college is still there**, and an
   external link is handed to the system browser rather than navigating the app. What remains
   unproven is precisely whether that executable starts under Windows. `.github/workflows/desktop.yml`
   builds and checks it on a `windows-latest` runner for exactly this reason.

   No installer was produced here either: NSIS needs Windows or Wine. The `nsis` block in
   `electron-builder.yml` is configured and will produce a `Setup.exe` unchanged on a machine that
   has one.

5. **Rate limiting is per-instance.** `InMemoryRateLimiter` counts requests in one process. Behind
   several instances a user gets the limit multiplied by the instance count. The `RateLimiter`
   interface exists so a shared backend can replace it without touching a caller.

6. **No import.** Export covers four formats; reading a backup back in was listed as optional for the
   MVP and is not built.

7. **No notifications.** Reminders are tasks the student sees when they open the app. There is no
   email or push, and the UI says so rather than implying a reminder will reach them.

8. **No screenshots in the repository.** Generate them by running `npm run dev` and visiting the
   routes; the README says the same.

9. **Colleges are user-entered.** ApplyPilot ships no college dataset and no deadline database. It
   records what the student tells it and repeatedly points them at official sources.
